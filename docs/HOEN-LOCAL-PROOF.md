# Shared machine identity for the Windows viewer

Status: the Windows broker and viewer hooks are implemented, with integrated validation in progress. A machine has one registered public-key fingerprint. The Windows viewer now obtains public host metadata and a channel-bound proof through the authenticated service instead of loading a separately seeded identity. Service installation and live IPC/session validation remain outstanding.

The implementation provides lookup and proof operations only, caps frames at 4096 bytes, and permits at most four concurrent broker tasks with timeouts outside the SCM loop. It preserves existing peer/session/executable authorization. The pinned `parity-tokio-ipc` commit `d0ae39b` uses Tokio `ServerOptions::new()` without changing its remote-client setting; Tokio 1.44.2 defaults that setting to true and maps it to `PIPE_REJECT_REMOTE_CLIENTS`. This source check establishes the requested creation flag, not a live remote-pipe rejection test. The service's identity runtime does not open the host worker's outbox or require hosting enabled. Private keys and machine bearer tokens are never returned. The viewer validates the response key, signature and binding after independently verifying the remote host handshake. The following design describes the security boundaries and remaining checks.

Coordinated Windows Rust 1.75 feature-on tests passed 38 cases, including redacted proof output, strict binding decoding, full-width network IDs in the IPC envelope, and viewer rejection of key/binding/signature/token substitution. Log: `%LOCALAPPDATA%\HoenBuildTools\remote-desktop-broker-test.log`. Regression surface is limited to feature-gated IPC variants/bounds, the Windows SCM broker dispatch, the Windows viewer connection selection and its parallel transport helper, and separate service identity initialization. Existing capture/input/clipboard implementations and non-Windows viewer selection are unchanged. No installed-service or real desktop connection was exercised by this run.

## Smallest integration

Keep the machine mailbox token and signing seed in the existing LocalSystem-protected host store. Add a narrow, versioned viewer broker to the existing Windows service pipe, not a key export or a general-purpose signing API. An authenticated local viewer uses the service's enrolled machine identity automatically; it never creates or registers a second identity. The mailbox principal and history identify that machine identity, not a claimed interactive username. Any enrolled mailbox identity remains eligible to access any registered hosting-enabled machine, subject to the existing transport policy.

1. Start the machine identity/mailbox worker and local broker independently of the desktop listener and hosting-enabled setting. First startup consumes the existing protected bootstrap and persists the generated key before registry operations. A missing, corrupt, or unavailable service enrollment fails closed; never generate a replacement because a read failed. Service unavailable means the viewer reports unavailable, not that it falls back to its separate enrollment.
2. Use a bounded typed request for looking up one host, returning only validated public registry metadata. The service uses its own pinned mailbox client and enrolled identity; callers cannot supply a mailbox URL, token, viewer identity, or fingerprint. Apply response size, timeout, and concurrency limits. A host-list UI is not implemented by this slice.
3. After the viewer independently verifies the chosen host's registered key, completes the encrypted host handshake and checks the actual socket/network guard, it sends a typed `IssueViewerProof { host, channel_binding: [u8; 32] }`. The service validates the host identity and request shape, issues a one-use grant for that host and binding using its own mailbox worker, and signs only the existing fixed-domain `viewer_proof_message(binding, grant_token)` with its enrolled key. It returns the existing `HoenProof` (public key, grant token, signature) over that authenticated local connection. No arbitrary payload signing, raw key export, token or proof logging, or caller-supplied principal is permitted. Apply bounded queues and a deadline, discard late/disconnected results, and fail closed on errors.
4. The viewer sends the proof only on that same verified channel, clears it after use, and retains current network checks. The host verifies the signature and consumes the grant against its own channel binding and independently checks both registered fingerprints. A caller-supplied host or binding is a request, not proof of its identity or channel; the service cannot itself attest the viewer's socket. Authorized local callers therefore can request grants for their selected hosts. Restricting who can use this machine identity is a local service authorization decision, not mailbox identity verification.

## Existing hooks and boundaries

`src/platform/windows.rs` creates `POSTFIX_SERVICE`, accepts a connection, calls `authorize_service_scoped_ipc_connection` for the active session and executable, then reads one `ipc::Data` request. `src/ipc.rs::connect_service` routes through `src/ipc/windows.rs::connect`, which checks the service pipe's SYSTEM owner and restricted DACL before application data. Existing listener ACL allows client access broadly, so the server-side active-session and executable checks are essential; preserve them for every new operation and verify their exact semantics with Windows tests. Name squatting can deny service but must not authenticate a fake server. Do not treat this pipe as a general-purpose local authorization facility.

The service loop bounds the initial request read to one second and dispatches broker operations to at most four tasks, each with bounded mailbox and response timeouts. It enforces the frame limit before decoding. The existing `Data` derives `Debug`; use a separate redacted payload or ensure the proof and grant can never be formatted or logged. Check that the underlying pipe implementation rejects remote clients, or explicitly enforce local-only peer access before using it for this operation. Test both server and client authentication; do not assume pipe naming or executable path alone proves a principal.

`src/hoen/runtime.rs` must separate machine enrollment/identity startup from host-listener startup so the broker works even when hosting is disabled. `src/hoen/mailbox_worker.rs` already has typed `list`, `lookup`, and `issue` operations. Change `src/hoen/transport.rs::Transport::connect` to use the broker for lookup and proof after `handshake::viewer` and `recheck`, rather than accepting a local `sign::SecretKey` and mailbox worker. `src/client/io_loop.rs` obtains the broker-backed viewer context instead of `runtime::viewer()`'s independently seeded store. Adapt `src/hoen/authorization.rs::issue_proof` so its service-side caller constructs only the fixed proof, without expanding the signing surface. Host-side `consume_proof` remains authoritative; do not use the peer's self-reported ID as principal.

The local authorization boundary is intentionally shared by authorized viewer processes in the permitted Windows session. A compromised permitted process can act as this machine identity and obtain a proof; the private key still remains in the service. If per-person mailbox attribution is required later it needs a separate authenticated enrollment design, not a self-reported name. The service is a required dependency for this viewer path. This design does not establish that a same-machine loopback desktop connection is permitted by the current network policy.

Before claiming integration, test service startup and restart with an unchanged registry fingerprint, viewer use with hosting disabled, service absence and corrupt enrollment, disallowed sessions and fake pipe servers, malformed/oversize and saturated requests, and token/channel/host substitution and replay rejection. Run the real Windows pipe and service tests as well as the cryptographic unit tests. Implementation is present; deployment and real desktop acceptance remain outstanding.

## Local Windows pipe evidence (2026-11-06)

The five `ipc::ipc_windows::tests` passed against the final source, including real named-pipe peer PID/session checks, rejection of an oversized frame before decoding, rejection of a different executable, and the existing untrusted-server/extra-instance checks. The feature suite also passed all 38 selected tests. Logs: `%LOCALAPPDATA%\HoenBuildTools\remote-desktop-real-pipe-tests.log` and `remote-desktop-pipe-hoen-tests.log`. Windows CI now explicitly runs the pipe suite with the mailbox feature enabled; the `hoen` name filter alone does not select these tests.

These tests run in the local test process, not an installed LocalSystem SCM service. They do not prove unattended capture or successful client-to-service authentication in deployment. The session boundary is based on the OS session ID, not whether that session is unlocked; a permitted process can remain authorized while the desktop is locked. The client is launched from the service's same protected executable path as documented in [installation](HOEN-INSTALLER.md).

Mailbox-mode worker startup now skips the legacy image-wide `RuntimeBroker_rustdesk.exe` cleanup, preventing it from terminating a stock RustDesk privacy broker. Feature-off behavior is unchanged. The previously recorded shipping artifact predates this startup guard and must be rebuilt before installation.
