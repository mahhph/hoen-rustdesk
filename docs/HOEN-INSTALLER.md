# Windows installation and machine identity

## Current implementation

The GUI is **Remote Desktop Client**; the Windows background service is **Remote Desktop Service**, SCM name `RemoteDesktopService`. Phase 1 installs one payload in `Program Files\Remote Desktop Service`. Launch `rustdesk.exe` in that protected directory without arguments for the client; SCM launches that same executable with `--service`. A viewer launched from a build folder or another installation path is rejected by the service broker's exact executable-path check. Separate product roles do not require separate copies of the binary. Do not weaken this check to accept a writable build directory.

The service reuses the machine's existing mailbox identity and bearer. `scripts/remote-desktop-bootstrap.ps1` reads the existing client configuration and reviewed identity and trust configuration, validates their contents, and writes a one-time machine-DPAPI transfer under SYSTEM/Administrators-only permissions. Inputs are read once; reviewed input digests are checked before provisioning. No credential is placed in command-line arguments or ordinary logs. New bootstrap files do not require a local IP address; older enrollment files remain readable.

On first startup, the LocalSystem host runtime validates the transfer, generates its signing seed only when its protected store is confirmed absent, seals it with LocalSystem DPAPI, verifies readback, then consumes the transfer. Corrupt or conflicting existing state is never silently replaced. Runtime state uses the Windows known folder `ProgramData\Remote Desktop Service State\host`; history storage is protected before bootstrap consumption. The viewer requests host metadata and channel-bound proofs through the authenticated service broker. It receives neither the machine bearer nor private signing key and needs no separate viewer enrollment. See [broker boundary and tests](HOEN-LOCAL-PROOF.md).

At host startup the operating system selects a local address for reaching the mailbox. The host binds that address and updates the registry after binding its listener. Outgoing connections let the operating system select an address for the target host. This avoids relying on a saved DHCP address, but the current registry advertises only one address: a machine with several active paths may need additional discovery or relay support. Registration eligibility is not a liveness lease. HTTPS validates the supplied trust root, hostname/IP SAN and recorded leaf fingerprint before credentials are transmitted. The production SAN-less certificate still needs replacement; the verifier must not be bypassed.

The user confirmed that the network path is not an authorization rule. Connections require the encrypted channel and mailbox proof regardless of path. The current implementation uses direct TCP; relay transport remains unimplemented. The live network-change disconnect test was explicitly waived; transition handling remains implemented but that behavior is unverified in a live session.

## Installer lifecycle

Production hardening is tracked in [production stories](PRODUCTION-STORIES.md). The first PRD-01 increment adds `scripts/remote-desktop-firewall.ps1`, separately invoked with `-Action Validate|Configure|Remove -ListenerPort <approved-port>`. Validate is the default and does not mutate policy. Configure and Remove require elevation. The helper owns only `RemoteDesktopService.Inbound.v1`, verifies its marker and executable/port/filter scope, and refuses conflicting rules or policy-query failures. It permits the configured TCP port for the installed executable across profiles and addresses; mailbox cryptographic authentication remains the access policy. An enabled rule is not proof of remote reachability.

Install now persists public `installation` metadata (schema, listener port and firewall ownership) inside its protected manifest. Activate validates the rule; uninstall removes it only if this installation created it. Pre-existing matching rules are not claimed. Legacy installations require explicit `AdoptFirewall` with a reviewed configuration digest and independently confirmed existing port while stopped/disabled; the encrypted service enrollment is not read. Existing manually configured rules, including `HoenRemoteDesktopServiceTCP42830`, are not adopted or removed. A crash between rule creation and durable metadata can leave a rule requiring administrator inspection; no crash-atomic firewall/SCM transaction is claimed.

`scripts/remote-desktop-upgrade.ps1` adds protected staging, content-verified replacement and restore of the retained previous payload. Upgrade/Restore require a clean stop and no installed payload processes. These actions do not change service state, credentials, history or firewall policy; activation and post-update identity/connection verification remain explicit. See the [controlled test guide](INSTALLER-TEST-GUIDE.md), including interrupted-staging and recovery-workspace limits. Existing installer `Rollback` means uninstall, not previous-version restore.

`scripts/remote-desktop-service-installer.ps1` supports these explicit actions:

- `Plan` is read-only and produces the payload hash manifest. With `ExpectedManifest`, it checks the exact payload against a previously reviewed manifest.
- `Install` requires elevation, the reviewed manifest, existing mailbox client-config path and approved-config path. It refuses an existing target/service, creates the protected installation, provisions the encrypted bootstrap and creates a disabled LocalSystem service. It does not start the service.
- `Activate` verifies installed files, permissions and exact SCM identity, changes startup to Automatic and starts the service with bounded status polling. On failure it attempts to stop and disable the service. SCM Running alone does not establish host readiness.
- `Deactivate` verifies ownership, disables the service and requests stop without stopping dependent services implicitly. It requires a successful SCM exit result, not only the Stopped state.
- `Rollback` requires the exact owned service to be disabled/stopped and the payload unchanged. It removes only owned installation objects and preserves encrypted runtime/bootstrap/history state. It refuses foreign files or directories, an unsuccessful service shutdown, and any running instance of the installed executable (including the client GUI). An unreadable path for a running RustDesk executable also prevents rollback. This is a preflight check, not an atomic guarantee against a later process launch; file-removal failures still propagate and no process is killed by the installer.

Stock RustDesk install, update, uninstall and service-control commands are blocked in mailbox builds. No broad image-name kill or unrelated-service removal is part of this installer. The native runner uses an absolute sibling DLL with restricted loading for its feature check; a missing DLL also rejects legacy pre-core service control. That narrow feature-off change is intentional. Import failures return a nonzero native process exit.

## Worker supervision and rollback safety update

Mailbox-mode service control now latches STOP in process, including before service IPC is ready. Worker supervision runs on elapsed-time checks independently of idle IPC timeouts. Startup failures back off through 1, 2, 4, 8, 16 and 30 seconds; only 30 seconds of observed live process time resets that delay. Process existence is not desktop readiness. On a session change the service retains the old worker's handle until its exit is confirmed, and a failed process query never authorizes a duplicate worker.

Close requests verify that the main pipe's server PID matches the exact owned process handle. Shutdown reports StopPending, waits up to 10 seconds for confirmed child exit, and reports a nonzero service failure if exit is unconfirmed. The installer rejects that failed result and refuses rollback while an installed client/host remains running. It does not kill unrelated processes. A timed-out worker can remain alive: failure is surfaced rather than claiming successful shutdown or safe removal.

The Windows mailbox GUI now uses the service's host IPC and does not start a user-owned host as a fallback. A mailbox worker encountering occupied main IPC exits without terminating the other process. These changes preserve feature-off and non-Windows startup paths. The shipping artifact at `40870ebf6` includes this update; build timings and hashes are recorded in [Windows evidence](HOEN-WINDOWS.md). Live SCM startup/stop, locked/signed-out access and desktop acceptance are still outstanding.

Validation on Windows with Rust 1.75 passed 40 mailbox tests, all five real-pipe tests and the GUI startup subprocess test. The feature-off build passed that same GUI startup check plus three unauthorized-admission regressions. Logs: `%LOCALAPPDATA%\HoenBuildTools\remote-desktop-supervision-tests.log` and `remote-desktop-supervision-feature-off.log`. The installer guard script passed its ten scenarios in both Windows PowerShell 5.1 and PowerShell 7.6.9, without service or process mutations. CI now runs the feature-enabled GUI check and installer guards explicitly. The new supervisor's actual LocalSystem launch/stop lifecycle still needs installed-service testing; deterministic scheduling tests do not establish that outcome.
