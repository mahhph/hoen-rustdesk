# Hoen remote-session history: RustDesk integration design

Status: the durable outbox, worker and feature-gated native lifecycle hooks are implemented; combined validation and end-to-end deployment verification remain outstanding. A recorded begin means verified host-side authorization and successful display enumeration, not capture readiness or viewer receipt. The mailbox implementation and its exact current contract are in the sibling `mailbox-integration/docs/REMOTE-SESSION-HISTORY.md`; reconcile the live service rather than replacing it wholesale. No conclusion about unattended access follows from this design.

## What the existing lifecycle proves

- `src/server.rs::identity_handshake` sends the **host's** signed identity and negotiates stream encryption. The controller's ephemeral key in this exchange is not an enrolled viewer identity. Some paths and older peers allow other transport behavior; the integration must explicitly verify the security properties it requires.
- `src/server/connection.rs::on_open` posts an existing `new` audit before login. It is not a connected session.
- `Connection::send_logon_response_and_keep_alive` performs password/approval, optional 2FA, and trusted-device checks, sets `authorized`, classifies the session and then constructs the login response. `authorized = true` alone is too early: later display initialization or trusted-device enrollment can fail. For a remote desktop the narrow candidate hook is immediately after the final `enroll_trusted_device` succeeds and only if `res.has_peer_info()` is true, before `res` is moved into the response. This proves host-side authorization and initialization, not that the viewer received the response: `Connection::send` currently logs/swallows send errors. Do not label it viewer-confirmed. Filter to remote desktop, not file transfer, port forwarding, terminal or camera.
- `Connection::on_close` is guarded by `self.closed` and can run on many error and normal paths; the loop later calls it again. The first call after a recorded open is the candidate one-time close hook. A process crash, kill, OS shutdown or power loss may bypass it. There is no reliable close hook for those cases.
- `lr.my_id`, name, platform, IP, RustDesk session ID and `controlled_context.conn_audit_ref` are not by themselves proof of an enrolled viewer. `connection.rs` explicitly describes `my_id` as self-reported. Password/TOTP or manual approval proves authorization under that policy; it does not identify a particular device when secrets are shared. The existing trusted-device path can validate a token, but is optional, may fall back to password/TOTP, and exposes no verified, mailbox-bound principal at the candidate hook. Do not promote its self-reported `DeviceInfo` into an identity without a reviewed binding and an explicit verified credential result.
- Existing `post_conn_audit` is a different API: it sends its own payload including peer fields, uses a per-connection in-memory unbounded channel, and its `post_audit_async` retry is time/attempt bounded. It neither persists its outbox across restarts nor speaks the mailbox endpoint. Do not redirect it to the mailbox or treat its successful call as durable history.

## Required identity binding before reporting

Provision an owner-controlled enrollment mapping from a cryptographically verified viewer credential to its authenticated mailbox principal, with the host's own mailbox identity independently authenticated (it may equal the viewer identity). All authenticated mailbox users may access registered hosting-enabled machines; identities must not be restricted to the old `mac`/`windows` pair. The mailbox source now accepts a server-configured enrolled identity list including Lenovo; production registry/identity reconciliation is still required before deployment. The mapping must be local trusted configuration or an authenticated, integrity-protected registry, not a field selected by the viewer. A viable new protocol is a challenge signed by an enrolled viewer private key, bound to this particular authenticated encrypted connection, host identity, challenge and purpose; the host verifies the signature, enrollment and revocation before it resolves the principal. Define replay resistance and a precise transcript/channel binding before implementation. A fresh challenge alone must not become a bearer assertion transferable to another channel. Protect private keys and enrollment changes using OS facilities and explicit trust decisions.

Alternatively a reviewed RustDesk trusted-device integration could expose the successfully verified credential's stable internal handle and bind that handle to the mailbox principal, but only when the proof actually succeeds on that connection; password/TOTP fallback, manual approval, failed/revoked proof and self-reported metadata must not inherit the binding. This route needs code and threat review and is not currently implemented. Either route must fail closed for attribution when proof or configuration is missing, ambiguous, changed, revoked, or insecure. Do not invent a client identity or claim the session was centrally tracked. Verified identity remains mandatory for admission, but history is best-effort: unavailable or slow local persistence must not reject an otherwise authenticated session. Log history failures without credentials, and do not silently weaken RustDesk authentication or change legacy paths when this feature is off.

The current mailbox authenticates the **reporting host** with its mailbox bearer token; it cannot independently verify the RustDesk peer. Securely provision host token and pinned mailbox TLS certificate, and keep them out of arguments, URLs, logs, event payloads and the outbox. The prior prototype's certificate-pin statement refers to its own mutual-TLS protocol; RustDesk's signed-host exchange is not a client certificate and must not be described as one.

## Proposed wire and persistence behavior

After host-side authorization, successful desktop initialization, and verified enrollment binding, generate an independent random UUID `sessionId` and random UUID `eventId`. Persist the following exact request before network delivery:

```
POST /v1/remote-sessions
{"sessionId":"<uuid>","eventId":"<uuid>","client":"mac","initiatorRole":"host"}
```

The `client` shown is illustrative and must come from the verified mapping. Omit `protocolVersion`: the current mailbox field is the prior Hoen protocol's 1–255 number and must not be filled with a RustDesk version or a fabricated value. The mailbox derives `host` from the bearer and creates `connected`, with `requested_at` null and a server-side `connected_at`. Confirm that the mapping's configured local host matches the actual authenticated mailbox identity; expose a configuration error instead of sending mismatched identities. No peer-supplied actor or timestamp is sent.

On `on_close` after a durable create intent, enqueue a separate event with a fresh stable event UUID:

```
POST /v1/remote-sessions/<sessionId>/events
{"eventId":"<uuid>","type":"ended","reason":"normal"}
```

Reason above is illustrative. Map typed, locally known conditions to the API's finite reason set (`normal`, `user_disconnect`, `network_error`, `authentication_failed`, `protocol_error`, `host_error`, `viewer_error`, `timeout`, `cancelled`). Unknown/ambiguous close causes need a conservative agreed mapping; never forward `on_close`'s arbitrary `reason` string or exception text. Use `failed` only when the host has evidence of failure, and do not synthesize successful `ended` after a crash. A connected heartbeat may be sent as `{ "eventId": "<uuid>", "type": "heartbeat" }`; schedule at a bounded rate and keep it metadata-only. Each event records one observation, not a guarantee the peer remains connected.

Use a small durable local outbox containing only endpoint, immutable request body, stable IDs and ordering metadata; keep credentials separate. Restrict file/directory permissions, use crash-safe atomic commit with data and directory synchronization appropriate to the OS, and recover after restart. Serialize sends per session: do not send heartbeat or terminal event until the create response is durably acknowledged; never reorder a terminal before earlier retained events. A lost response may mean the server committed: retry the *identical* request and IDs. Accept `201` for a new event or `200` with `duplicate: true` only after validating a well-formed expected JSON response and matching session ID; treat other 2xx, malformed JSON and mismatched IDs as unconfirmed. Retry transport failures, 408, 429 and 5xx with bounded exponential backoff and jitter; retain records on disk across process restart. Surface permanent 4xx (including 401/403/409) as a non-sensitive actionable reporting error; do not blindly change IDs or delete conflicting records. Delete/mark delivered only after a confirmed response is durably recorded.

Bound disk consumption and rate, including outages: reserve capacity for a terminal event before recording an auditable session, coalesce only heartbeats that have not yet been durably enqueued, and never silently discard a pending create or terminal event. If a durable write, quota, or history token configuration fails, log history as unavailable while allowing an otherwise authenticated connection. A durable outbox cannot guarantee central delivery during indefinite outage or after local disk destruction. If the server has only `requested` or `connected`, clients must display unknown/stale based on `last_seen_at`, never infer an end. A failed create that never reached the server may leave no central row at all; local pending/error status must make that visible.

Do not hold RustDesk locks across await, block the connection runtime with HTTP or disk I/O, or create nested Tokio runtimes. A bounded handoff to a dedicated durable writer/worker is required; it must acknowledge local persistence before the feature claims the event is recorded. Protect recovery from concurrent service instances and define ownership during service/session transitions. No clipboard, screens, keyboard events, authentication material, arbitrary error strings or remote URLs containing credentials enter persistent audit data.

## Smallest implementation slice and checks

1. Implement an isolated, feature-gated durable outbox and typed mailbox client with no RustDesk hooks; test exact retry after lost response, restart, transactional ordering, error handling, disk-full reporting, response validation, and redaction. Make it disabled by default.
2. Separately define and test the enrolled viewer proof/mapping on each supported transport; reject unverified identities and insecure fallback. Establish certificate/key rotation, revocation and service configuration before enabling attribution.
3. Add one thin hook at the successful remote-desktop response point and one guarded hook at first close; pass only verified principal and typed reason into the module. Add tests for failed authentication/display initialization, duplicate close, one connection/reconnect, crash/missing end, and absent/invalid binding. Decide how multiple RustDesk channels belonging to a single user session are represented before claiming one row per user session; a connection-level row is the honest initial scope.
4. Test mailbox history end to end against an isolated instance and inspect database records; restart host and mailbox under injected failures. Verify feature-off behavior, Windows service/session transitions and actual devices before claiming support. Do not deploy this source over the newer live mailbox without merging its later web/identity changes and migrating its database.

Expected regression surface for a future change: one new feature-specific module and narrow host connection lifecycle hooks, plus the specifically reviewed viewer identity-proof plumbing; no rewrite of existing audit, transport or capture paths. This document changes no runtime paths.
