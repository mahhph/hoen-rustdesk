# Windows Hoen enrollment and installer design (not implemented)

This is a design for a future installer and bootstrap, not install instructions or evidence of unattended support. No service, firewall rule, credential, or live setting was changed while preparing it. The existing mailbox-mode Windows binary must not be installed alongside RustDesk until the naming and handoff gaps below are resolved and tested.

## Current code and blockers

* `src/hoen/enrollment.rs` recognizes `--hoen-import-viewer` and `--hoen-import-host` and reads a bounded bundle from standard input. `runtime::import_enrollment` validates and seals it; the command does **not** supply or authenticate a transport into the LocalSystem identity. Windows UAC elevation to an administrator is not LocalSystem, and the viewer's DPAPI-encrypted blob cannot be decrypted by the service. Do not solve this by copying ciphertext, using machine-scope DPAPI, putting plaintext in a file, command line, environment, registry, audit record or generic service IPC.
* `credentials::ProtectedStore` uses current-user DPAPI with separate role entropy, verifies the process token identity, rejects thread impersonation and expects owner-only, non-reparse protected directories. Host purpose requires LocalSystem. `runtime.rs` uses `%LOCALAPPDATA%\HoenRemote\viewer` and `%ProgramData%\HoenRemote\host`, with a protected inheritable `history` child. Treat environment variables as untrusted inputs at the installer/service boundary: use the appropriate Windows known-folder API and validate the final protected directory. The viewer and service have separate OS protection scopes, but currently serialize the same schema; a protected store does not prevent compromise by code running as the same principal or a privileged administrator, nor rollback of an older valid blob.
* `core_main.rs` routes import errors to `CoreMainAction::ExitFailure`, but the Windows Flutter FFI in `src/flutter.rs` returns a null pointer on that error and `flutter/windows/runner/main.cpp` returns `EXIT_SUCCESS` for null. A bootstrapper must not infer import success from this current exit code. Add an explicit non-secret result status with reliable nonzero process exits and test the actual Flutter runner and pipe disconnect/error paths.
* `src/platform/windows.rs::run_service` reports SCM Running before host launch, polls for session changes, starts `--server`, and uses service-scoped IPC with peer session/executable checks. In `windows.cc`, `LaunchProcessWin(..., as_user=false)` uses the token from `winlogon.exe`, but its fallback can use `sihost.exe`; do not assume every worker is LocalSystem. An incorrect token causes the Hoen host store to reject access. Secure desktop capture/control, logoff, signed-out startup, SAS and crash/input cleanup require real end-to-end tests; code paths alone do not prove support.
* The upstream default `APP_NAME` is `RustDesk`. SCM dispatcher and installer service names, named pipes, config locations, tray and other resources derive from app name. Existing install/remove logic can stop/delete the app-name service and uses image-name `taskkill`; running it with RustDesk names can disrupt an existing installation. A separate executable path alone is insufficient.
* `runtime::initialize` compares a mailbox identity's registered public-key fingerprint against the locally derived signing key. Independently generating different viewer and host seeds for the **same mailbox identity** causes a mismatch. Decide and implement either separately registered role identities supported by the mailbox, or a single per-device key accessible via a narrowly authenticated signing service; duplicating a key into both DPAPI scopes is a different security tradeoff. The mailbox's actual identity/role and secret API capabilities must be checked; do not fabricate registration, assume a mutable global secret authenticates a host, or publish a CA/signing private key.
* `host::run` advertises hosting only after binding and suspends on network change, but the current registry flag is not a lease and is not reliably cleared on crash, loss of mailbox connectivity, or removal. `OnceCell` and monitor lifecycle also need deliberate restart/re-enrollment behavior. A service being Running is not host readiness.

## Proposed minimal bootstrap

1. Build a Hoen-specific, feature-gated signed package. Before any `Config` or IPC static is initialized, establish a stable, immutable Hoen application namespace. Reserve a distinct service name such as `HoenRemoteHost`, distinct display name, binaries under a Hoen-only protected installation directory, Hoen-only `APP_NAME`/config/pipe/tray/mutex/update/ARP identifiers, and an explicit independent network port. The exact service name used by SCM creation, dispatcher and control handler must match even if the UI app name differs. Audit every upstream name-dependent path, window class, uninstall, shortcut, driver and image-name process termination; make removal target verified Hoen-owned process IDs, never `RustDesk.exe` or another service. Do not rely on runtime mutable custom-client branding for isolation.
2. An installer running with the required elevation installs the disabled-by-default Hoen service under its dedicated SCM identity as LocalSystem, and creates only its protected program directory. Service configuration, executable and dependencies must be protected from unprivileged writes and reparse substitution. Prefer supported SCM APIs with explicit service binary path/arguments rather than shell-built commands; ensure rollback is ownership-aware. SCM Running should mean only that the supervisor and local bootstrap endpoint are available; UI and registry must separately report host readiness. No network listener or advertisement before validated enrollment, approved network, keys, authentication, and worker readiness.
3. Viewer enrollment happens under the signed-in user's process token and seals that user's viewer bundle in its own protected DPAPI store. Host enrollment must execute in the LocalSystem service identity and write its separate protected store and inheritable history directory. Have the service generate and retain its host private signing material locally; export only public fingerprint for registration. Use distinct mailbox identity/role material only after the identity model above is resolved.
4. Implement a one-shot, bounded bootstrap named pipe scoped to Hoen, on the local machine with an explicit restrictive DACL for LocalSystem and the user who initiated setup, `PIPE_REJECT_REMOTE_CLIENTS`, short timeout, and one narrowly defined enrollment operation. The server must obtain the client PID and token from Windows, verify the exact intended user SID and interactive session and the expected installed client image; it must not accept a caller-claimed identity. Before sending any sensitive host-scoped mailbox credential or trust config, the client must verify the server PID belongs to the actual Hoen SCM service, runs as LocalSystem and has the expected protected installed image. Validate executable ownership/signature or pinned digest according to a reviewed update policy; a path or claimed PID alone is not proof. Defend pipe squatting, replay, cancellation and partial messages; do not expose arbitrary commands or generic SYSTEM execution. Keep the protocol and errors free of secrets.
5. The service validates the proposed host bundle, exact CA trust and approved interface/network IDs, seals atomically under LocalSystem, and returns only success/failure over that authenticated pipe. The viewer must verify the explicit result; any disconnect or ambiguous result is failure until the service performs a safe read-back/status check. Never return a bearer, private key or decrypted bundle. Zero transient buffers where practical, bound lengths, and grant a temporary bootstrap channel only for the authorized installation transaction. DPAPI remains a local at-rest boundary, not an authorization mechanism for IPC.
6. Start the RustDesk session worker only after verifying its actual token is LocalSystem and the intended session; use Hoen-only IPC and stop on mismatch. Supervise startup, locked/unlocked/logoff transitions and cleanup. Bind only to the approved home interface and accept only a verified mailbox grant on the authenticated direct channel. Windows network changes close listeners and sessions; authenticated identity and LAN policy are independent. A false readiness result, network change, unavailable mailbox, invalid profile/route, missing credential, invalid protected ACL or worker failure must fail closed.

## Install, rollback and acceptance

Record the exact build hash, service name, file list, configuration ownership, existing Hoen installation state and user-approved network. Before changing anything, identify an existing non-Hoen RustDesk service/process/config and leave it untouched. Make setup idempotent: on a name/path collision not demonstrably owned by Hoen, abort without overwriting. Provision viewer and service stores under their actual identities, then verify health and authenticated binding before advertising. Local-only setup must not open a public listener, configure public discovery or change routers. Firewall setup, if implemented, needs a precise approved-interface/address-scoped rule and a record for rollback; no firewall changes are performed by this design.

Rollback must stop and delete **only** the verified Hoen service, close its worker and listener, remove only Hoen-owned shortcuts/files/rules that this install created, and restore a previous Hoen version/config if an update failed. Avoid broad image-name kills or deleting user data by default. Explicitly handle a possibly stale mailbox registration: revoke/disable where supported, but never claim the remote record was removed if offline. Preserve encrypted enrollment and outbox unless the user explicitly requests removal, and document consequences of retaining, rotating or revoking keys. Do not delete or replace unrelated RustDesk or mailbox services. Installation, removal and recovery must return observable failure status.

Before claiming readiness, exercise new install, rollback from every intermediate failure, uninstall and reinstall, side-by-side RustDesk, user/admin/SYSTEM token boundaries, rejecting an unauthorized pipe client/server, tampered/cross-role DPAPI data, missing/insecure ACLs, crashes, reboot, network changes, revoked mailbox grants and missing mailbox features. Then validate signed-in, locked and signed-out sessions on Windows Home/Pro in both target-machine directions. Do not persist screen, clipboard, keystrokes, token, key or bootstrap payload in logs.
